Treat the KV cache like virtual memory.

vLLM borrowed the OS playbook: pages, page tables, and on-demand allocation. The result was 2–4× throughput on the same GPU — by deleting the fragmentation that conventional engines were silently bleeding.

Before vLLM, an LLM serving engine reserved a contiguous KV slab per request — sized for the worst case, sequence-length-wise — and watched 60–80% of GPU memory sit empty. The fix is the same one OS designers landed on in 1962: stop pretending memory is contiguous. Use pages, build a per-process page table, allocate on demand.

The OS analogy same problem, same fix

The mapping is almost too clean. Sequences are processes. KV-cache pages are virtual pages. A block table is a page table. Physical GPU blocks are physical frames. The kernel allocates on page fault; PagedAttention allocates on token append.

Memory waste where the gigabytes go

The chart below is, more or less, why vLLM exists. Static reservation pre-allocates max-seq for every request and almost everything is wasted. Dynamic contiguous pre-allocates a max guess and external fragmentation eats the rest. Paging keeps everything tight; only the last block has a tiny tail.

Copy-on-Write for beam search fork without the copy

Beam search runs $k$ candidate continuations in parallel. They share a long prefix and only diverge at the very end. Copying the whole KV cache per beam wastes massive memory; PagedAttention shares the prefix blocks across beams and only copies a block when one beam writes to it.

Three flavors of fragmentation and what paging fixes

Internal

Last block is partially full — the tail. Average waste = block_size / 2 tokens per sequence. Reduced by smaller block size.

External

Free memory is scattered in chunks too small for any new request. Eliminated by paging — any free block fits.

Reservation

Pre-allocating max_seq_len even when most requests are short. Eliminated by on-demand allocation.
