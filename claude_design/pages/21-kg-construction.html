Let the LLM build its own graph.

LightRAG and HippoRAG turn unstructured text into entity-relation graphs at ingest time. The graph becomes a second retrieval modality — multi-hop traversal where vector search alone fails.

Ingest cost vs vector

Vector search finds documents that look like the query. It can\'t answer "find people connected to Alice through three or fewer relationships" — that\'s a graph traversal. KG construction wants the best of both.

Extraction · the LLM does the work

Feed each chunk to the LLM with a prompt: "extract entities (with types) and relations (subject, predicate, object) as JSON." Cache and dedupe. Run a second pass to merge near-duplicate entities ("Alice", "Alice Smith", "A. Smith"). Cost: ~$0.50 / 1k chunks with a small model.

LightRAG vs HippoRAG

LightRAG · 2024

Dual-level retrieval

Two parallel queries: low-level (entities and relations relevant to the query) and high-level (themes and concepts). Both feed the LLM context.

  • Cheap incremental updates
  • Lower extraction cost than GraphRAG
  • Hybrid with vector search
HippoRAG · 2024

PageRank over KG

Inspired by hippocampus indexing. Build a KG once. At query time: identify seed nodes from the query, run personalized PageRank, return top-N nodes\' source documents.

  • Multi-hop reasoning · single retrieval call
  • Beats iterative RAG on MuSiQue / 2WikiMQA
  • Synaptic vs episodic memory analogy

When it earns its keep

KG construction is 3× the ingest cost of plain vector RAG. Use it when:

  • › Queries need multi-hop reasoning ("who works on the team that built X")
  • › Corpus has structured entities (people, products, events) with stable types
  • › You need to answer "summarise everything about X" across the whole corpus
  • › Avoid for: short, factoid queries · cost-sensitive ingest · heterogeneous web-scale text
